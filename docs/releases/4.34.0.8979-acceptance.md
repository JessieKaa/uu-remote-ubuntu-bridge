# UU Remote 4.34.0.8979 acceptance

This document records the privacy-safe evidence used to accept UU Remote
4.34.0.8979 for guarded, login-preserving promotion on the Ubuntu bridge.
Proprietary binaries, raw logs, account identifiers, tokens, device
identifiers, controller addresses, and desktop content remain local.

## Static review

The 4.33 and 4.34 binaries were compared using semantic strings, RIP-relative
string cross-references, complete surrounding control flow, targeted
`objdump` disassembly, and exact `xxd` byte capture.

The constructor default remained an exact shifted match. The constructor
setting load, setting reader, and runtime setter retained the same behavior
with changed call displacements and layout. Each replacement forces only the
existing user-mode input selection while leaving surrounding calls and
control flow unchanged. The approved manifest contains the complete original
and replacement bytes for all four sites.

## Disposable-prefix validation

1. The signed-in 4.33 prefix was stopped cleanly and copied twice.
2. The official 4.34 installer and approved patch were applied to only one
   copy using `--prefix-only --upgrade-existing --skip-account-login`.
3. The login registry digest and full per-user GameViewer cache were unchanged.
4. All shared account-bearing files were unchanged.
5. UU added only `setting.ini`, containing non-account remote-assist guide UI
   state. The promotion gate now excludes exactly that path and continues to
   hash every other shared file.
6. The patched server and audited health-monitor backup verified successfully.

## Controller and stability validation

The disposable 4.34 prefix was started through a transient canary bridge while
the original 4.33 prefix remained untouched.

- The server reported `4.34.0.8979` and established its UU service channels.
- The local FreeRDP relay connected to GNOME RDP on port 3391.
- A controller disconnected and reconnected successfully.
- Control and clipboard channels opened successfully.
- The content-free input broker recorded six successful mouse injections
  through the focused RDP route with no input values captured.
- The same server and relay PIDs remained alive for 297 seconds.
- No crash dump, forced exit, server re-injection, or `devcon` stall appeared.
- A second verification passed the manifest, binary, health monitor, hooks,
  broker, keyboard route, account state, and controller-history checks.

The canary verifier also reported four expected infrastructure differences:
the production service name was inactive, the transient unit used the source
checkout directly, its systemd descriptor limit differed, and its temporary
GNOME setting differed from the configured production value. Live sockets,
the explicit RDP port, and the guarded descriptor count were healthy. These
differences are removed when the accepted release is installed through the
normal production unit.

## Acceptance

The maintainer confirmed promotion after the hash-bound patch workflow was
explained. The production transaction must still take a complete prefix
snapshot, preserve protected login state, verify twice across at least 270
seconds, and roll back automatically on any failure.
